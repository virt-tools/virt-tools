How the numbers work

  • Grid points. An N × N × N 3D LUT holds N³ points, each with three channels, so the channel sample count is 3 × N³. A 33-point cube holds 35,937 points and 107,811 channel samples; a 65-point cube holds 274,625 points.
  • Runtime memory. The table is 3 × N³ stored channel values of the chosen width: 4 bytes for float32, 2 bytes for float16 or uint16 and 1 byte for uint8. Memory does not depend on the file's decimal count — that is a text serialisation detail.
  • .cube text size. Each point is written as three values with d decimals, separated by spaces, so a line is 3 × (d + 2) + 3 bytes including the newline. The estimate adds a 64-byte header allowance for TITLE, LUT_3D_SIZE and the domain lines and excludes optional comments, so a real file can be slightly larger.
  • Input step. Grid points sit 1 / (N − 1) apart in the normalised 0–1 domain. A 33-point LUT steps by 0.03125 (3.125 %), so a 10-bit input has about 32 distinct values between samples.
  • Sampling cost. A tetrahedral sampler reads 4 corners per output sample and a trilinear sampler reads 8. Each corner fetch returns three channels, so the traffic figure is samples × corners × 3 × bytes per second. Real hardware caches neighbouring lookups, so treat the traffic number as an upper bound for uncached random access.
  • This is table arithmetic, not a quality score. A larger grid reduces interpolation error but costs memory and cache locality, and a LUT's accuracy still depends on how it was generated. The page performs no storage, uploads or network requests.
