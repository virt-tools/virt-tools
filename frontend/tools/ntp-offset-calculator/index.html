NTP Offset Calculator

Work out how far a server's clock sits from yours from one NTP exchange. The page applies the RFC 5905 offset and delay formulas to the four timestamps, reports the round-trip delay and the range the true offset can occupy. Everything is computed locally.

Enter each timestamp in seconds with up to 12 decimals. T1 and T4 come from your clock and T2 and T3 from the server's, so any fixed origin works on each side — Unix time, seconds since 1900, or elapsed seconds — provided both sides count from the same epoch, since the offset is simply the difference between the two readings.

One exchange gives four timestamps: T1 when the client sent the request, T2 when the server received it, T3 when the server sent the reply and T4 when the client received it. RFC 5905 reads them as the offset of the server clock relative to the client clock, theta = ½[(T2 − T1) + (T3 − T4)], and the round-trip delay delta = (T4 − T1) − (T3 − T2). A positive offset means the server clock reads ahead of yours, so adding it to a local reading gives the server's time and the local clock is that far slow. The request and the reply are assumed to take the same time on the wire, so the true offset can sit anywhere within plus or minus half the delay of the estimate; a wider delay means a looser answer. A negative delay is arithmetically possible, as RFC 5905 notes when the two clocks run at different frequencies, but it cannot come from a sound exchange, so the page refuses the figures instead of reporting one. Real NTP daemons take many such samples and filter them rather than trusting a single exchange. Nothing is uploaded, stored or sent anywhere.
