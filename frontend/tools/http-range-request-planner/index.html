HTTP Range Request Planner

Enter the size of a representation and the Range header a client would send. The page parses the header the way a server does — byte offsets from zero, open-ended and suffix ranges, clamping, satisfiability — and shows the status, the Content-Range and Content-Type that come back, the bytes actually sent, and each part of a multipart response. Everything runs in your browser; nothing is uploaded, stored or sent anywhere.

Request

The length of the resource as sent, in whole bytes. 10 MiB is 10485760; the size is what makes a range satisfiable or not.

If-Range makes the Range conditional: when the validator no longer matches, the whole representation is sent instead.

For example bytes=0-1023, bytes=1024-, bytes=-500, or several ranges separated by commas. Only the bytes unit is defined for HTTP.

    What this does not do

    • This models what a well-behaved origin server should answer, not what yours will. A server may ignore a Range header it cannot use, refuse a header with many overlapping or unordered ranges, and a cache or proxy may recombine or ignore the request.
    • Range is evaluated only when the request would otherwise be a 200. A conditional GET that comes back 304 Not Modified never carries a partial body, and preconditions such as If-Match that fail short-circuit before this point.
    • Ranges are counted on the bytes as sent, so with a content coding applied the offsets refer to the encoded sequence, not to the decoded resource.
    • Sizes are limited to 1 to 1,099,511,627,776 bytes (1 TiB) and to at most 32 ranges in one header. A zero-length representation only allows a non-zero suffix range, and is not modelled here.
