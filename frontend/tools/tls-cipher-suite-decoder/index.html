TLS Cipher Suite Decoder

Turn a suite name like TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 or a code like 0x1301 into the key exchange, authentication, bulk cipher and hash it names, or read a whole ClientHello offer at once.

One value, or several separated by spaces or commas

Codes are hexadecimal, written 0x1301 or 1301. Names are the IANA registry names; the lookup ignores case and accepts the value list a ClientHello sends.

A cipher suite is a pair of bytes: the code 0x1301 is the bytes 0x13 and 0x01, which is why the registry prints it as {0x13,0x01}. TLS 1.3 suite names carry only the AEAD and the hash (TLS_AEAD_HASH), because the key exchange and authentication moved into the handshake: TLS_AES_128_GCM_SHA256 says AES-128-GCM with the HKDF-SHA256 hash and nothing about certificates. Names of TLS 1.2 and earlier read TLS_<key exchange>_WITH_<bulk cipher>_<MAC>, and the key-exchange token also names the authentication, so ECDHE_RSA is ephemeral ECDH with an RSA signature. In the AEAD suites (GCM, CCM, ChaCha20-Poly1305) the trailing hash is the PRF rather than a record MAC, and the RFC 6655 CCM suites name no hash at all because their PRF is fixed at SHA-256; the page says which case it found. 0x00FF and 0x5600 are signalling values (secure renegotiation and the fallback indication), not suites a server can select, and the GREASE values of RFC 8701 — 0x0A0A, 0x1A1A and so on — are deliberately unassigned. The registry's Recommended column is its own: Y recommended, N not recommended (which the registry notes can mean limited applicability rather than a flaw) and D discouraged, which should not be negotiated. The page decodes names and codes; it does not judge whether a suite is right for your server, and it never contacts the network — the registry table it uses is compiled into this page.
