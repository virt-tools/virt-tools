Reverse DNS Zone Builder

Reverse DNS maps an address to a name under in-addr.arpa (IPv4) or ip6.arpa (IPv6). This page turns a prefix into its reverse zone: the zone apex, the RFC 2317 CNAMEs a classless delegation needs, and the PTR owner name for every address in the range. Everything runs locally — no lookups, uploads or accounts.

Prefix

For example 192.0.2.0/24, 192.0.2.64/26 or 2001:db8::/32.

How the reverse zone is built


An IPv4 reverse name writes the address octets backwards and adds in-addr.arpa: 192.0.2.10 becomes 10.2.0.192.in-addr.arpa.. Reverse zones are normally delegated on a /24 boundary, so 192.0.2.0/24 owns 2.0.192.in-addr.arpa. and the last octet is the relative owner name inside it.


    

  • A prefix longer than /24 covers only part of that zone. RFC 2317 handles it by delegating the range to its own zone — 192.0.2.64/26 becomes 64-127.2.0.192.in-addr.arpa. — and adding one CNAME in the parent zone for each address, so resolvers follow the delegation.
    • 

  • A prefix shorter than /24 spans several /24 zones; the page lists the zones it covers instead of inventing a single apex.
    • 

  • An IPv6 reverse name uses one hex digit per label, written backwards: 2001:db8::/32 owns 8.b.d.0.1.0.0.2.ip6.arpa.. Zones are delegated on nibble boundaries, so a prefix that is not a multiple of 4 is rounded down and the status line says so.
    • 

  • PTR lines are listed while the block holds at most 256 addresses. Larger blocks show the apex only, because the record set would be far too long to be useful here.
    • 

  • The page emits no SOA or NS records: those need a primary server, a serial and a contact that only you can choose. It also does no lookup and no DNSSEC signing, so the records are a starting point for your zone file, not a working zone on their own.
